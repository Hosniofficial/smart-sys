# بنية المشروع

## 1. نظرة عامة

SmartSys هو مشروع ERP متعدد المستأجرين ويعتمد على ثلاث طبقات رئيسية:

1. Backend API عبر PHP + Slim 4
2. Frontend عبر Vue 3 + Pinia + Axios
3. Database عبر MySQL مع migrations

كل طبقة مسؤولة عن جزء واضح من التطبيق، مع فصل منطق الأعمال عن طبقة الاستلام HTTP.

## 3. طبقات التطبيق

### Backend

الـ API في موقع `api/v1/` يتبع نمط شائع من:

- Handlers: تتولى استلام الطلب، التحقق من المدخلات، وزيادة الاستجابة
- Services: تعالج القواعد التشغيلية، التحقق من الصلاحيات، والمنطق المالي أو المخزني
- Repositories: تغلف الوصول إلى البيانات
- Middleware: يحمل سياق المستأجر والفرع والمصادقة والاشتراك

### Frontend

الواجهة في `SmartSys-Frontend/` تستخدم:

- Vue 3 + composition API
- Pinia لحالة التطبيق المشتركة
- Router للتنقل
- Axios عبر إعدادات موحدة في `src/config`
- composables في الحالات المتكررة

## 4. نمط العمل المطلوب

### PHP

- لا تضع منطق خاص بالعمل داخل `Handler` إلا للالتقاط والتنسيق.
- فضّل `Service` لكل عملية من أكثر من خطوة.
- استخدم `prepared statements` في كل عمليات SQL.
- أضف التحقق من `branch_id` و`tenant_id` في كل نقطة حساسة.

### Vue

- اجعل الصفحة تستدعي الخدمات عبر الـ store أو الـ composable المناسب.
- لا تنسخ منطق الطلب داخل كل صفحة.
- عند التعامل مع الفرع: استخدم `useRequiredBranch` أو `useBranchIsolation` عند الحاجة.
- حافظ على مصدر واحد للبيانات شائع، ولا تكرر نفس القيم في كائنات متعددة.

## 5. إدارة الفرع والمرتبطة بالمستخدم

الفرع هو جزء أساسي في التطبيق، خصوصًا في التقارير والعمليات المالية والمخزنية. لذلك:

- لا يعتمد التقرير على `all branches` إلا إذا كان هذا النمط واضحًا ومسموحًا.
- إذا كانت الصفحة تتطلب فرعًا محددًا، يجب إجبار الاختيار قبل تحميل البيانات.
- احرص على ضبط سياق المستخدم والفرع في كل service/handler المرتبط بالبيانات.

## 6. التوثيق

تُخزن الوثائق الأساسية في `docs/`، مع إبقاء الروابط من `README.md` مرتبطة وموجزة.

للمطور الجديد، المسار النموذجي هو:

1. قراءة `README.md`
2. قراءة `docs/README.md`
3. قراءة `docs/DEVELOPER_GUIDE.md`
4. مراجعة `database/README.md`

## 7. معايير التسليم الأولي

قبل التسليم، نحتاج أن نضمن:

- أن الـ frontend يبني بنجاح
- أن الـ API لا يرفع ملفات حساسة
- أن جميع المستندات المهمة موضوعة في `/docs`
- أن الملفات المؤقتة والمتكررة تم حذفها
- أن استخدام الفرع والـ pagination والـ page header موحدًا قدر الإمكان

## 8. ملاحظات أخيرة

المنهج الصحيح في هذا المشروع هو: التوثيق المختصر، التناسق في بنية المشاريع، والتقليل من الملفات المؤقتة والتكرار. الهدف الأساسي هو أن تكون قاعدة الشفرة واضحة، يمكنها أن تُفهم دون معرفة سابقة من مطور سابق.
