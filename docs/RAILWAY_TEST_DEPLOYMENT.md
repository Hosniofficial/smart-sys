# دليل تجربة SmartSys على Railway

## المقصود بالخطة

نعم، يمكن تشغيل النظام كله على Railway. المقصود هو إنشاء **ثلاث خدمات منفصلة داخل مشروع Railway واحد**، وليس وضع التطبيق وقاعدة البيانات في خدمة واحدة:

```text
المتصفح
   │
   ▼
واجهة Vue/Vite ── HTTPS ──► PHP API ── اتصال داخلي خاص ──► MySQL
```

| الخدمة | ما تشغّله | هل تحتاج عنوانًا عامًا؟ |
|---|---|---|
| Frontend | ملفات الواجهة المبنية من `SmartSys-Frontend` | نعم |
| API | تطبيق PHP ونقطة الدخول `public/index.php` | نعم |
| MySQL | قاعدة بيانات التجربة | لا؛ تتصل بها خدمة API داخليًا |

كل خدمة لها إعدادها وتشغيلها، لكنها تظل ضمن المشروع نفسه وتتصل عبر عناوين Railway ومتغيرات البيئة. لا ينبغي فتح قاعدة البيانات للإنترنت لمجرد أن الواجهة أو الـAPI تحتاج إليها.

## الخيار المقترح للتجربة

**الأبسط والأقل إعدادًا:** استضافة الـAPI وMySQL على Railway، واستضافة الواجهة على Cloudflare Pages. عندها يصبح لدينا خدمتان على Railway وخدمة واجهة على Pages، مع بقاء الواجهة والـAPI منفصلتين.

**إذا كان المطلوب أن تكون الخدمات الثلاث كلها على Railway:** استضف الواجهة أيضًا كخدمة ويب مستقلة. يلزم إعداد طريقة لبناء Vue ثم تقديم مجلد `dist` مع دعم روابط Vue Router المباشرة (SPA fallback).

في الحالتين، الواجهة في المتصفح هي التي تتصل بعنوان الـAPI العام عبر HTTPS؛ والـAPI وحده يتصل بـMySQL عبر الشبكة الخاصة. لا يتصل المتصفح بقاعدة البيانات مباشرة.

## وضع المستودع الحالي

المستودع يحتوي على تطبيق PHP والواجهة وتعليمات قاعدة البيانات، لكنه لا يحتوي حاليًا على إعداد نشر جاهز لـRailway مثل `Dockerfile` أو ملفات تهيئة Railway. لذلك فهذا الدليل يشرح التصميم والإعداد المطلوبين، **ولا يعني أن النشر يتم بمجرد ربط المستودع أو أن النظام قد نُشر واختُبر على Railway**.

قبل النشر الفعلي، يجب تجهيز طريقة تشغيل PHP في حاوية أو بيئة Railway مناسبة، تشمل Composer وامتداد `pdo_mysql` وخادم HTTP يستمع على المنفذ الذي توفره Railway (`$PORT`) ويحوّل طلبات الـAPI إلى `public/index.php`. ملف `.htaccess` الموجود خاص بـApache ولن يطبّق تلقائيًا على خادم آخر.

## تجهيز قاعدة بيانات اختبار

1. أنشئ مشروعًا وبيئة **تجربة منفصلة** على Railway، ثم أضف خدمة MySQL إليه.
2. اترك قاعدة البيانات خاصة داخل المشروع، ولا تضف لها TCP Proxy عامًا ما لم توجد حاجة إدارية واضحة.
3. أنشئ قاعدة بيانات فارغة مخصصة للاختبار، واستعد المخطط وبيانات التهيئة واتبع الخطوات في [دليل قاعدة البيانات](../database/README.md). حزمة المخطط خالية من بيانات التشغيل؛ الـseed يحتوي بيانات التهيئة العامة فقط، وليس نسخة بيانات قاعدة العملاء.
4. لا تستخدم نسخة قاعدة إنتاج فعلية أو بيانات عملاء حقيقية لهذا الاختبار. لا تستعد ملفات SQL فوق قاعدة فيها بيانات؛ استخدم قاعدة فارغة مخصصة.
5. لا تشغّل migrations يدويًا على قاعدة مستخدمة قبل مراجعة حالتها ونسخها احتياطيًا. النشر هنا للاختبار فقط.

Railway يوفّر لمثيل MySQL متغيرات مثل `MYSQLHOST` و`MYSQLPORT` و`MYSQLUSER` و`MYSQLPASSWORD` و`MYSQLDATABASE`. بعض الإعدادات تعرض أيضًا `MYSQL_DATABASE` و`MYSQL_ROOT_PASSWORD`؛ اربط متغيرات SmartSys بنظائرها (`DB_HOST` و`DB_PORT` و`DB_USERNAME` و`DB_PASSWORD` و`DB_DATABASE`) عبر مراجع Railway، ولا تنسخ كلمات المرور في المستودع أو المحادثات. لا تستخدم حساب `root` لاتصال API الدائم؛ أنشئ مستخدم تطبيق محدود الصلاحيات. اترك قاعدة البيانات خاصة ولا تضع عنوانها العام في إعداد الـAPI.

**حالة مخطط المصدر:** يحتوي التطبيق الحالي على migrations حتى `038`. أزيلت حزم SQL التاريخية وأداة استيراد Railway القديمة من المستودع بعد نقل قاعدة الإنتاج إلى Aiven. استخدم قاعدة اختبار فارغة، واتبع تعليمات migrations الحالية في [دليل قاعدة البيانات](../database/README.md)؛ لا تستعد dump قديمًا أو تشغّل migrations على قاعدة تحتوي بيانات دون فحص السجل ونسخة احتياطية قابلة للاستعادة.

تنبيه بيانات: ملف seed المعتمد يستبعد دور `branch_manager` العالمي وإسناداته الـ36 وفق قرار النشر، رغم وجودها في القاعدة المحلية. لا تُعد استيراد بيانات المستأجرين أو التشغيل إلى بيئة اختبار مشتركة.

## خدمة الـAPI على Railway

اربط خدمة الـAPI بجذر المستودع؛ يجب أن تُثبّت الاعتماديات من `composer.lock`، وتُقدّم محتويات `public/` كنقطة دخول HTTP. اضبط الخدمة لتستمع على `0.0.0.0:$PORT`، ثم أنشئ لها نطاق HTTPS عام من إعدادات Railway.

المسارات المستخدمة في التطبيق تتضمن `/api/v1`. لذلك عيّن عنوان الـAPI العام النهائي بعد نشر الخدمة، مثل:

```text
https://<api-service-domain>/api/v1
```

قد يختلف اسم النطاق الفعلي الذي تخصصه Railway؛ استخدم النطاق الظاهر في إعدادات الخدمة، ولا تفترض أن المثال أعلاه نطاق صالح.

## متغيرات البيئة

أضف القيم في إعدادات الخدمة المناسبة، لا في ملفات Git. اربط بيانات MySQL بمراجع Railway إلى خدمة قاعدة البيانات، وأدخل الأسرار يدويًا كقيم سرية:

| المتغير | القيمة المطلوبة للتجربة |
|---|---|
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |
| `DB_HOST` | مرجع `MYSQLHOST` من خدمة MySQL |
| `DB_PORT` | مرجع `MYSQLPORT` |
| `DB_DATABASE` | مرجع `MYSQLDATABASE` |
| `DB_USERNAME` | مرجع `MYSQLUSER` |
| `DB_PASSWORD` | مرجع `MYSQLPASSWORD` |
| `DB_CHARSET` | `utf8mb4` |
| `JWT_SECRET` | سر عشوائي جديد وقوي خاص ببيئة التجربة |
| `JWT_REFRESH_SECRET` | سر عشوائي جديد ومختلف عن `JWT_SECRET` |
| `CORS_ALLOWED_ORIGINS` | أصل الواجهة المنشورة فقط، مثل `https://<frontend-domain>` |
| `CORS_ALLOW_ALL` | `false` |
| `APP_URL` | عنوان الواجهة المنشور، لا عنوان localhost |
| `APP_BASE_PATH` | `/smartsys/api/v1`، وفق إعداد المسار الأساسي في التطبيق |
| `API_BASE_URL` | أصل خدمة الـAPI فقط، مثل `https://<api-service-domain>` دون مسار |
| `ADMIN_API_URL` | للرابط الإداري عند إعداد cron: `https://<api-service-domain>/smartsys/api/v1/admin/subscriptions/cron` |
| `CRON_SECRET` | سر عشوائي جديد إذا ستُستخدم مهمة cron |
| `TWO_FA_ENCRYPTION_KEY` | مفتاح تشفير قوي إذا ستُستخدم ميزة المصادقة الثنائية |

لا تنسخ قيمًا حقيقية إلى هذا الملف أو إلى `.env.example` أو المستودع. لا تستخدم مفاتيح التطوير الموجودة في `.env.example`، ولا تفعّل `CORS_ALLOW_ALL` أو `APP_DEBUG` على خدمة عامة. إعدادات SMTP مطلوبة فقط إذا أردت اختبار التحقق بالبريد أو استعادة كلمة المرور؛ ومفاتيح بوابات الدفع لا تلزم ما لم تختبر التكامل معها. إعداد cron اختياري للتجربة الأولية؛ إذا فعّلته فاستخدم `ADMIN_API_URL` الكامل أعلاه واختبره يدويًا أولًا.

## نشر الواجهة

### الواجهة على Cloudflare Pages

- اربط المستودع واختر `SmartSys-Frontend` مجلدًا أساسيًا للمشروع.
- أمر البناء: `npm ci && npm run build`.
- مجلد الملفات الناتجة: `dist`.
- أضف متغير البناء `VITE_API_BASE_URL` بقيمة عنوان الـAPI الكامل، مثل `https://<api-service-domain>/api/v1`.
- أضف نطاق الواجهة المنشور نفسه إلى `CORS_ALLOWED_ORIGINS` في خدمة الـAPI.
- اختبر فتح صفحات داخلية مباشرة بعد النشر للتأكد من معالجة SPA fallback.

### الواجهة على Railway

أنشئ لها خدمة ويب منفصلة عن الـAPI. اضبطها على `SmartSys-Frontend`، وابنِ الملفات باستخدام `npm ci` ثم `npm run build`، وقدّم محتويات `dist` بخادم ملفات يستمع على `$PORT` ويعيد طلبات المسارات الأمامية غير الموجودة إلى `index.html`. عيّن `VITE_API_BASE_URL` **وقت البناء** إلى عنوان الـAPI العام الكامل، ثم انشر الخدمة وأضف أصلها إلى `CORS_ALLOWED_ORIGINS`.

وجود `VITE_API_BASE_URL` أثناء البناء مهم: قيمة `VITE_` تُضمّن في ملفات الواجهة المبنية، وليست سرًا ولا تُقرأ كإعداد سري وقت تشغيل المتصفح.

## اختبار التجربة بعد النشر

1. تأكد أن خدمة MySQL تعمل، وأن الـAPI يتصل بها من دون كشف بيانات الاتصال في السجلات أو الاستجابة.
2. افتح مسار فحص الصحة إذا كان متاحًا على الخدمة، ثم اختبر مسار API عامًّا لا يتطلب تسجيل دخول.
3. افتح الواجهة عبر HTTPS، وسجّل حساب تجربة جديدًا من خلال تدفق التسجيل المعتاد.
4. اختبر تسجيل الدخول، تبديل الصفحات الداخلية مباشرة، واستدعاءات الـAPI من المتصفح. راقب تبويب Network بحثًا عن أخطاء CORS أو عناوين localhost.
5. اختبر عملية بسيطة في بيانات التجربة، مثل إنشاء سجل غير مالي، ثم اختبر سيناريو مالي تجريبيًا وتحقق من أثره في الشاشة والتقارير قبل استخدام أي بيانات مهمة.
6. أعد تشغيل خدمات API والواجهة وتأكد أن تسجيل الدخول والبيانات ما زالا يعملان؛ بيانات MySQL يجب أن تبقى محفوظة عبر إعادة نشر التطبيق.
7. راجع سجلات الخدمات والتنبيهات وحدود الموارد والتكلفة في لوحة Railway. لا تفترض أن التجربة مجانية أو أن الخدمة ستبقى متاحة دائمًا على خطة مجانية؛ الأسعار والحدود تتغير.
