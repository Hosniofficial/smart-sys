# دليل المطور

هذا هو المرجع الأساسي لفهم بنية SmartSys وطريقة تنفيذ التغييرات. عند تعارض مثال توثيقي قديم مع الكود الحالي، اتبع التنفيذ الحالي واختباراته ثم حدّث المرجع المتأثر.

## خريطة المشروع

```text
SmartSys/
├── public/                 نقطة دخول HTTP لخادم PHP
├── config/                 إعداد التطبيق وDI وتسجيل المجموعات والمسارات
├── app/routes/             تعريف مسارات API وربطها بالمعالجات والصلاحيات
├── api/v1/src/
│   ├── Handlers/           تحويل طلب HTTP إلى عملية واستجابة
│   ├── Middleware/         المصادقة والمستأجر والاشتراك والصلاحيات وغيرها
│   ├── Services/           قواعد العمل والعمليات متعددة الخطوات
│   ├── Repositories/       وحدات وصول للبيانات عند الحاجة
│   ├── Security/           سياسات وصلاحيات المجال
│   ├── Exceptions/         أخطاء المجال المعروفة
│   └── Utils/              أدوات مشتركة
├── database/migrations/    سجل تغييرات قاعدة البيانات المرتّب
├── tests/Unit/             اختبارات الوحدة والعقود
├── tests/Integration/      اختبارات التكامل، ومنها اختبارات MySQL
└── SmartSys-Frontend/
    └── src/
        ├── views/          صفحات التطبيق
        ├── components/     مكونات الواجهة القابلة لإعادة الاستخدام
        ├── stores/         حالة Pinia المشتركة
        ├── services/       خدمات API أو وظائف الواجهة المتخصصة
        ├── composables/    منطق Vue قابل لإعادة الاستخدام
        ├── router/         المسارات والحراسة والتنقل
        └── config/         إعداد Axios والتهيئة المشتركة
```

## تدفق الطلب

1. يرسل Vue الطلب باستخدام عميل Axios المشترك في `SmartSys-Frontend/src/config/axios.js`؛ استخدم هذا العميل بدل إنشاء عميل HTTP مستقل.
2. تُسجّل المسارات في ملفات `app/routes/` وتُحمّل مجموعاتها من `config/routes.php`.
3. تمر الطلبات المحمية عبر طبقات المصادقة JWT والمستأجر والاشتراك، ثم عبر صلاحية المسار المطلوبة.
4. يستقبل `Handler` الطلب، يتحقق من مدخلاته وسياقه، ويفوض منطق العمل إلى `Service` عند وجود قواعد أو أكثر من خطوة.
5. تنفذ الخدمة عمليات قاعدة البيانات وتعيد نتيجة أو خطأ مجال معروف؛ يحوّل المعالج ذلك إلى استجابة API متسقة.
6. تحدّث الواجهة الحالة المشتركة عند الحاجة عبر Pinia، وتترك حالة الصفحة/التركيب في الصفحة أو composable عندما لا تحتاج مشاركة.

المسار المعتاد لتعريف endpoint جديد:

- أضف المسار إلى ملف المجال المناسب في `app/routes/`.
- اربطه بـHandler مسجل في الحاوية عند الحاجة، وصرّح بوسيط الصلاحية المناسب.
- ضع قواعد العمل في Service، وأعد استخدام Repository أو Helper قائم بدل تكرار استعلام أو سياسة.
- أضف اختبارًا يثبت السلوك والحالات المرفوضة.

## قواعد تنفيذ التغييرات

### PHP وAPI

- اتبع أسلوب PHP الموجود في الملف والمجلد؛ المشروع يستخدم أسماء أصناف واضحة وتقسيمًا حسب المجال.
- تحقّق من المدخلات عند حدّ API، وأعد أخطاء تحقق مفهومة وفق نمط الاستجابات المستخدم.
- استخدم PDO prepared statements لكل مدخلات SQL. لا تركّب قيم المستخدم مباشرة في الاستعلام.
- لا تضع منطق المجال أو سلسلة تغييرات مالية/مخزنية كاملة داخل Handler؛ اجعل الخدمة مسؤولة عن قواعد العملية والمعاملة.
- استخدم المعاملات للعمليات التي يجب أن تنجح أو تتراجع كوحدة واحدة. في المحاسبة والمخزون، حافظ على اتزان القيود وترابطها مع حركة المصدر.
- استخدم الاستثناءات وأنماط تسجيل الأخطاء الموجودة. لا تخفِ الاستثناءات ولا تُرجع نجاحًا افتراضيًا بعد فشل.

### المستأجر والفرع والصلاحيات

- كل قراءة أو كتابة تخص بيانات منشأة يجب أن تبقى ضمن `tenant_id` الموثوق من سياق المصادقة؛ لا تعتمد على قيمة المستأجر القادمة من العميل لتحديد نطاق الوصول.
- العمليات المعتمدة على الفرع تحتاج سياق `branch_id` صريحًا، مع التحقق من أن الفرع متاح للمستخدم والمستأجر. لا توسّع التقرير أو العملية إلى كل الفروع كحل احتياطي صامت.
- أضف صلاحية API على المسار باستخدام `PermissionMiddleware` وثوابت `Permissions` المناسبة، ولا تعتمد على إخفاء زر في الواجهة كحماية.
- في الواجهة، أعد استخدام `useRequiredBranch` و`useBranchIsolation` أو النمط الأقرب الموجود في المجال لتوحيد اختيار الفرع وعزله.

### Vue والواجهة

- اتبع نمط Vue 3 المستخدم في الملفات المجاورة، وغالبًا `<script setup>`.
- استخدم Router للتنقل، وPinia للحالة التي تتشاركها الصفحات، وcomposables للمنطق التفاعلي القابل لإعادة الاستخدام.
- اجعل استدعاءات API تمر عبر Axios المشترك وخدمات المجال عند وجودها؛ تجنب نسخ إعدادات المصادقة ومعالجة الأخطاء داخل الصفحات.
- حافظ على حالات التحميل والخطأ والبيانات الفارغة بصورة ظاهرة للمستخدم. لا تستبدل الفشل بقيمة نجاح أو قائمة فارغة تخفي السبب.
- اتبع تصميم RTL والتوطين وأنماط المكونات الموجودة في الميزة نفسها.

## قاعدة البيانات والترحيلات

- كل تغيير دائم في المخطط يُضاف كملف migration جديد مرقّم في `database/migrations/` وفق أداة المشروع.
- لا تعدّل أو تحذف أو تعِد ترقيم migration سبق تسجيلها في قاعدة؛ أضف migration تصحيحية جديدة.
- افحص الحالة أولًا:

  ```powershell
  php database/migrate.php status
  ```

- لا تشغّل `up` إلا على قاعدة تطوير/اختبار معروفة وبعد مراجعة migrations المعلقة. في البيئات المشتركة أو الإنتاجية يلزم اعتماد وخطة نسخة احتياطية واستعادة ومراجعة سجل القاعدة.
- لا توجد حزم SQL تاريخية أو أدوات نقل خاصة بمزود الاستضافة في المستودع؛ راجع [تعليمات قاعدة البيانات](../database/README.md) وإجراءات migrations.
- تفاصيل سجل migrations وإجراءات التشغيل في [database/README.md](../database/README.md) و[database/migrations/README.md](../database/migrations/README.md).

## الاختبارات والتحقق

من جذر المشروع:

```powershell
# اختبارات الوحدة
vendor/bin/phpunit --testsuite Unit

# اختبارات التكامل (تتطلب قاعدة MySQL معزولة ومهيأة للاختبار)
vendor/bin/phpunit --testsuite Integration

# كل الاختبارات
composer test
```

تضبط `phpunit.xml` قاعدة الاختبار الافتراضية باسم `inventory_test`. تحقق من كود الاختبار قبل التشغيل؛ بعض اختبارات التكامل تنشئ مخططًا مؤقتًا أو تحتاج صلاحيات MySQL. لا تستخدم قاعدة تحتوي بيانات تشغيلية.

لبناء الواجهة:

```powershell
Set-Location SmartSys-Frontend
npm ci
npm run build
```

قبل التسليم، شغّل أصغر مجموعة اختبارات مرتبطة بالتغيير، وبناء الواجهة إن مسّ التغيير الواجهة، ثم راجع `git diff --check` وملخص الفرق.
